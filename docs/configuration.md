# Configuration

Configuration is read from environment variables. A local `.env` file supplies them for the Docker Compose stack and the engine. The public release ships only a placeholder `.env.example` — **no real values are published**. The table below lists every variable **name** from the reference `.env`, its purpose, a safe placeholder, and whether it is required. Placeholders are deliberately non-functional.

All database/embedding settings are read by `engine/src/core.js` (which also accepts plain environment variables in preference to the file). Credentials must be generated by the operator; the Docker Compose file only references them as `${...}`.

| Name | Purpose | Safe placeholder | Required? |
|---|---|---|---|
| `MEMORY_DB_USER` | PostgreSQL role used by the engine and compose healthcheck | `appuser` | Required |

| `MEMORY_DB_NAME` | Database name (production: `opencode_memory`; isolated tests: `opencode_memory_test`) | `appdb` | Required |
| `MEMORY_DB_PORT` | Host port mapped to container port 5432 (loopback only) | `54400` | Required |

## Safety defaults that must not be weakened

Two values are explicitly protected by the Phase 28 final report, the operational runbook, and the release audit. Change them only with explicit operator authorization and a documented reason:

1. `OPTIMIZATION_LEVEL=1` — the OBSERVE level. The optimizer may observe and recommend but does not autonomously execute actions. Raising it grants controlled-execution capability; automation is otherwise gated by explicit single-use approval. Preserve `1` unless you deliberately opt into controlled execution.
2. `HARNESS_SEMANTIC_LLM=0` — automatic semantic LLM calls are opt-in. Live measurement showed a 200-char real request taking roughly 46 seconds (and a 600-char request timing out at 300 seconds). Keeping it `0` preserves fast turn-end processing; `llm_test` remains available for on-demand checks. AI output is always a candidate with capped confidence and can never verify a memory, approve an action, or execute code.

Other safety invariants recorded alongside these: single-use workflow approvals, project isolation, no source rewriting, no auto-approval, no unrestricted process execution. See `docs/security.md`.

## Secrets handling

- `MEMORY_DB_PASSWORD` is a secret. It lives only in the local `.env` (already ignored by version control); publish only `.env.example` with a placeholder.
- `HARNESS_LLM_TRANSPORT=opencode-cli` means the Harness reuses OpenCode's own provider/auth — it does **not** hold a Harness-side API key. If a direct transport is configured instead, the API key is read only from a user-named environment variable (`HARNESS_LLM_KEY_ENV`, default `HARNESS_LLM_API_KEY`) and is never stored in code, logs, the database, or the dashboard. A redaction layer strips `sk-`, `Bearer`, and `AKIA`-style patterns before storage.
- Never paste real values into issues, docs, or logs. See `SECURITY.md` for the vulnerability reporting process.

## Additional names recognized in source (not present in the reference `.env`)

These are advanced, optional knobs read directly from the environment by individual modules. They are names only, with no values supplied here. Confirm behavior in the relevant source file before using them.

- Database/embeddings: `MEMORY_DB_HOST`, `MEMORY_EMBED_URL`
- LLM: `HARNESS_LLM_KEY_ENV`, `HARNESS_NODE_BIN`, `HARNESS_LLM_TIMEOUT_MS`
- OpenCode integration: `HARNESS_OPENCODE_DB`, `SQLITE3`
- Automation/reliability: `HARNESS_CLAIM_LEASE_MS`, `HARNESS_TRIAGE_INTERVAL_MS`, `HARNESS_LINK_INTERVAL_MS`, `HARNESS_WORKER_BATCH`, `HARNESS_TRIAGE_DUPLICATE`, `HARNESS_TRIAGE_NEAR`, `HARNESS_TRIAGE_MERGE`

## Honest limitations

- Defaults and compatibility are reported only for the tested local Windows scope (see `docs/compatibility.md`). No assumption should be made that untested platforms honor the same paths or shims.
- Presence of a variable does not guarantee runtime behavior; use the diagnostics in `docs/troubleshooting.md` to verify actual state.
